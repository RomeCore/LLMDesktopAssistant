# 1. Модель видимости агентов

## 1.1. Ключ автора

Ключ — **обычная строка**:

- парсится как `Guid` → это `AgentId`;
- иначе → это `UserLogin`.

Следствия, которые обязаны соблюдаться:

- **логин не может быть Guid-подобным** (иначе ключевые пространства пересекаются и восстановить
  принадлежность нечем) — правило валидации при создании пользователя;
- UI обязан рендерить ключ, который не резолвится в живого автора, как **«неизвестный автор»**
  (`agent:3f2a…`), а не молча прятать;
- **записи-сироты хранятся вечно, авто-удаление запрещено.** Удаление записи = возврат к дефолту =
  *расширение* видимости. Это fail-open, поэтому никогда не автоматически.

## 1.2. Запись оверрайда

```csharp
record VisibilityOverride
{
    bool IsVisible;                    // применимо ли правило
    bool OverrideIsVisible;            // задано ли явно (иначе — дефолт)
    FacetMask Facet;                   // маска фасетов
    bool OverrideFacet;                // задана ли маска явно (иначе — дефолт)
    PromptAuthorIdentity Identity;     // как рендерится автор этому получателю (см. 1.6)
                                       // отдельного Override-флага нет: единственный способ
                                       // сказать «не задано» — член Default
}
```

Хранится в `ObservableDictionary<string, VisibilityOverride>` (ключ — см. 1.1) + **дефолт отдельно**.

Дефолт + разреженные записи дают объединение white/blacklist без отдельных режимов:

| Что нужно | Как выражается |
|---|---|
| white list | `default = IsVisible: false`, у разрешённых авторов — явное `true` |
| black list | `default = IsVisible: true`, у запрещённых — явное `false` |
| «всё как обычно» | обе `Override*` = `false` → работает дефолт |

## 1.3. Две стороны и правило скрещивания

| | Сторона **отправителя** | Сторона **получателя** |
|---|---|---|
| Вопрос | «что я **отдаю**» | «что я **читаю**» |
| Природа | приватность | внимание / экономия контекста |
| Может выдать доступ | **да** | **нет** |
| Форма настроек | попарные записи + дефолт | **одна глобальная маска** «что читаю ото всех» |

**Правило скрещивания: всегда И. Режима И/ИЛИ НЕ существует.**

Почему: настраиваемый оператор слияния — это глобальная скрытая переменная, меняющая смысл каждой
записи в чате. После её введения на вопрос «почему A это видит?» нельзя ответить, не зная текущий
режим, а экспорт/бэкап настроек перестаёт быть исполнимой спецификацией.

**Зеркала настроек чтения нет.** Попарные записи живут только у отправителя. UI даёт редактировать
обе поверхности (и «что мы отдаём каждому агенту», и «что мы читаем у каждого агента»), но правка
со второй поверхности **биндится на себя в конфиге того агента** (пишется запись с ключом читателя в
словаре отправителя). Источник истины на пару — ровно один.

Следствия:

- противоречивых записей на пару не бывает в принципе → на оси «пара» тихих no-op не существует;
- редактирование чужой записи не даёт эскалации: правка «читать у B ничего» ложится как «B не отдаёт
  агенту A» и на других не влияет;
- **но И остаётся между двумя уровнями**: попарная запись отправителя × глобальная маска получателя.
  Значит резать может любая из двух, и **UI обязан показывать, какая именно сейчас режет** (иначе
  возвращаемся к тихим неработающим галкам).

## 1.4. Наследование

| Что | Наследуется? |
|---|---|
| Попарный словарь | **да** |
| Дефолт отправителя («что отдаю всем») | да |
| Глобальная маска чтения получателя | да |

Почему словарь можно наследовать: он читается как `TryGetValue(key) ?? default`, поэтому запись,
указывающая на отсутствующего автора, **инертна** — она не матчится и ни на что не влияет. Цена —
размер файла настроек и лишний глубокий трекинг (`ChangeTracker` дёргает автосейв на каждую правку).

Реальное исключение из «влияет только на размер» — **scope правки**: у глобальных агентов GUID
стабилен, поэтому запись, поднятая на уровень `Application`, работает **во всех чатах сразу**. Это
может быть желаемым поведением, но должно быть видимым.

- **дефолтный уровень для попарных записей — `Agent`** (локально для чата); `Application` / `Profile`
  — осознанное повышение;
- аффорданс: кнопки **«копировать» / «вставить» на комбобоксе уровня наследования**, при этом вставка
  пишет **в тот уровень, на который смотрит пользователь**, и кнопка обязана об этом сообщать
  («вставить в Application — применится во всех чатах»).

## 1.5. Фасеты

**Решение: плоская маска.** Сознательно, чтобы не плодить enum-ы; смысл («что это за флаг и как его
показывать») пинится на уровне UI.

Обязательное требование к реализации: **единый литеральный список дескрипторов фасетов**
(`flag, group, label, hint`), из которого генерится UI, локализация, документация и любая группировка.
Иначе появится второй параллельный `switch`, интерпретирующий маску, и добавление фасета будет
требовать правок в N местах.

Состав маски:

| Флаг | Уровень | Примечание |
|---|---|---|
| `ReasoningContent` | внутри сообщения | |
| `Content` | внутри сообщения | включает наследников `AdditionalMessagePart` |
| `Attachments` | внутри сообщения | `AttachmentMessagePart` |
| `NativeAttachments` | внутри сообщения | `NativeAttachmentMessagePart` |
| `ToolCalls` | внутри сообщения | |
| `ToolCallArguments` | внутри сообщения | |
| `ToolCallResult` | внутри сообщения | |
| `MessagesWithToolCalls` | **уровень сообщения (гейт)** | см. ниже |

**`Name` из маски исключён** — идентичность однозначна, а маска умеет только OR-ить режимы. Переехала
в отдельное поле записи оверрайда — `VisibilityOverride.Identity` (см. 1.6), то есть лежит рядом
с маской, а не внутри неё.

> **Правило гейта.** Если `MessagesWithToolCalls` выключен и в сообщении есть тул-коллы — маска к
> этому сообщению **не применяется вообще**, сообщение выпадает целиком (а не «рендерится без коллов»).

Почему гейт нужен и почему он не дублирует `ToolCalls`: у assistant-сообщения с коллами есть
**нарративная преамбула** («О, давай проверю, что у тебя там в проекте…» + вызовы). `ToolCalls = false`
уберёт вызовы, но оставит фразу — то есть целится в другое. Ценность гейта **сценозависима**: в
кодинге преамбула — мусор, в ролевой игре («мастер кидает кубики посреди рассказа») такое сообщение
обязано остаться. Поэтому это per-agent предпочтение, а не универсальное правило.

Открытый вопрос по перекрытию: `AttachmentMessagePart : NativeAttachmentMessagePart : AdditionalMessagePart`
— это цепочка подтипов, поэтому `Content` / `Attachments` / `NativeAttachments` пересекаются.
Нужно решить: фасет — это **фильтр типов частей** (побеждает самый производный) или **поле-уровневая
редакция** (часть остаётся, `NativeAttachment = null`). «Показать метаданные файла, но не отдавать
нативный payload» выражается только вторым способом.

## 1.6. Идентичность автора

**Идентичность — это отдельная ось, а не фасет** (не член маски), и она задаётся **с двух сторон**.

### 1.6.1. Сторона отправителя

Отправитель объявляет, как он появляется в промпте. Истинный класс сообщения синтезируется на уровне
сообщения (из `IsUserLike`) и складывается с объявлением отправителя — получается конкретное значение:

```csharp
enum PromptAuthorIdentity
{
    Default,        // «не задано» / как объявил себя отправитель (единственный sentinel: Override-флага нет)
    Anon,           // [MESSAGE FROM ANON. AUTHOR]
    NamedUser,      // [MESSAGE FROM USER 'name']
    NamedAgent,     // [MESSAGE FROM AGENT 'name']
    UnnamedUser,    // [MESSAGE FROM ANON. USER]
    UnnamedAgent,   // [MESSAGE FROM ANON. AGENT]
}
```

Без `Default` (шесть значений минус sentinel) это было бы полное произведение
`{имя: есть | нет} × {класс: USER | AGENT | скрыт}` — все комбинации осмысленны, дырок нет, поэтому
плоский enum корректнее флагов. `Default` тут — не «седьмая комбинация», а маркер «не задано»;
он нужен именно потому, что отдельного `Override`-флага у идентичности нет.

**`IsUserLike` ≠ идентичность.** `IsUserLike` (в `ChatAgentInformation`) — флаг **поведения** сообщения:
раскрытие сообщений, группировка по раундам (юзеры начинают раунды), позиционирование в UI (юзер справа,
«чистый» агент слева). На промпт-идентичность он влияет только как источник **истинного класса**.

### 1.6.2. Сторона получателя

У читателя тоже есть политика идентичности, со своим **дефолтом и попарными оверрайдами** (дефолт
накладывается, оверрайд уточняет). При этом значение читателя обязано быть **kind-agnostic** — читатель
управляет только **уровнем раскрытия**, а не классом:

```csharp
enum PromptAuthorIdentityLevel { Auto, Named, Unnamed, Anon }
```

Читатель **физически не может** объявить автора юзером, если тот агент: это была бы не рестрикция, а
ложь. Класс принадлежит отправителю, уровень — обеим сторонам.

### 1.6.3. Итоговое значение для рендера

```
Истинный класс сообщения (IsUserLike)
  + объявленная идентичность отправителя      →  PromptAuthorIdentity (конкретное)
  + политика читателя (дефолт ⊕ оверрайд)     →  PromptAuthorIdentityLevel
  =  итоговый заголовок сообщения
```

Это **не про приватность** (приложение — поле для общения нейронок): имя просто не рендерится в
заголовке. Ценность — управление атрибуцией для модели, а также то, что порядок `ExecutionStages`
не детерминирован, поэтому позиционная идентификация ненадёжна. Раскрытие класса влияет только на
рендер и на то, знает ли модель, что перед ней агент или юзер.

**Имена сейчас резолвятся живьём на сборке** (`ChatPromptBuilder`: `senderDescriptor.Info.Name ?? id[..8]`,
для юзеров `FindByLogin(...)?.GetAgentShownName()`). Штампование идентичности/имени в сообщение
отложено в следующие рефакторинги. **Принятая цена:** переименование агента или переключение режима
идентичности ре-рендерит весь регион сообщений (изменение байтов в середине префикса → кеш мёртв,
«модель помнит другую историю»).

> **Асимметрия, которую это фиксирует:** фасеты **ретроактивны** by design (скрыл задним числом —
> сразу подействовало), идентичность — **живая** (то же самое, но ценой ре-рендера региона).

## 1.7. SelfVisibility

```csharp
[Flags]
enum SelfVisibility
{
    None = 0,
    Messages = 1 << 0,                // видеть свои предыдущие сообщения
    Reasoning = 1 << 1,               // видеть свои рассуждения вообще
    OnlyThisRoundReasoning = 1 << 2,  // МОДИФИКАТОР: рассуждения только в текущей цепочке
                                      // (классический CoT), по дефолту ВЫКЛЮЧЕН
}
```

- `OnlyThisRoundReasoning` — **модификатор, а не независимый выбор**: без выставленного `Reasoning` он
  инертен (рассуждений нет — ограничивать нечего). Нормализуется в одном месте, а не проверяется
  в каждом потребителе.
- **По дефолту `OnlyThisRoundReasoning` выключен** → агент видит **весь свой CoT** с первых сообщений
  (текущее поведение). Настройка — опт-ин: включается ради экономии контекста и ради совместимости
  с провайдерами, которые ругаются на отправку reasoning для старых assistant-сообщений.
- **Фасеты на свои сообщения не накладываются вообще** (не carve-out, а правило: self = без фильтров).
- `OnlyThisRoundReasoning = true` — агент видит **только** рассуждения текущей цепочки: проход
  **с конца к началу** по effective set; если на пути встретилось хоть одно сообщение не от того же
  автора (включая самое первое, т.е. последнее по порядку) — reasoning блокируется целиком. Никаких
  `ChainId`, ни персиста, ни штампов: правило позиционное и производное.
- Прогон считается **по видимым (effective) сообщениям** и **только по настоящим сообщениям авторов**.
  **Инъекции прогон не рвут** (memory digest, вложения, дельты SCM, чекпоинты): иначе ретеншен CoT
  начнёт мигать в зависимости от того, сработала ли подмешка памяти в конкретном ходу.
- Подавление — на рендере; история не переписывается.
- Механика на цепочке: на первом шаге цепочки (после юзерского) прогон пуст → показывать нечего; на
  втором шаге предыдущее assistant-сообщение уже в истории и оно своё → прогон непуст → агент видит
  свою мысль с первого шага. Классический CoT получается сам, без спецлогики.

Мотивы настройки: (1) экономия контекста; (2) совместимость с провайдерами, которые ругаются на
отправку reasoning для старых assistant-сообщений. Второй мотив **не** распространяется на инъекции:
они не несут reasoning.

## 1.8. Чекпоинты и деклассификация

- **Семантика включительная:** сообщение-носитель чекпоинта **само не видно**, регион **после** него
  видим. (Соответствует текущему коду: `AllowContextShields` → `break` при обратном проходе.)
- Чекпоинты — **общий рез для всех агентов** (артефакт сообщения), в отличие от видимости, которая
  per-reader.
- `Summary` + `ContextShield` сливаются в **`CheckPoint`** с опциональным контентом и `Kind`.
  Требуется миграция BSON-схемы (сейчас `SummaryViewModel.Summary` — `string`, `ContextShieldViewModel`
  — пустой маркер).
- **Контент чекпоинта — граница деклассификации.** Всё, что в него попало, видно всем, кто читает
  чекпоинты, и не гейтится правами авторов исходных сообщений.
- **Поверхность утечки ограничена фасетом `Content`.** Суммаризация строится только на основном
  контенте сообщений и **игнорирует reasoning, вложения и тул-коллы** — они в саммари не попадают
  никогда.
- Остаточный случай (принят осознанно): агент, которому запрещён `Content` от автора B, всё равно
  узнаёт содержание B через чекпоинт, автоматически, без намерения пользователя.
- Известная опция на будущее: фрагменты с провенансом автора (`— B: предложил Z`), где фрагмент без
  автора виден только тем, кто может читать `Content` всех контрибьюторов, а «опубликовать для всех»
  — ручным опт-ином.

## 1.9. Что видимостью не управляется

Системный контент — память, скиллы, промпт-части, хуки, внутренние agentic-таски — **не автор**.
Видимость по автору на него не распространяется; включение регулируется собственными настройками
агента («включить скиллы», «включить блок памяти» и т.д.).

## 1.10. Инварианты видимости

1. `visible = sender.gives(reader) AND reader.allows`, поэлементно по маске. Оператора слияния нет.
2. Свои сообщения фасетами не фильтруются никогда.
3. Невидимое сообщение **подавляется на рендере**, а не удаляется из истории.
4. Удаление записи оверрайда запрещено автоматически (fail-open).
5. Правку «что я читаю у B» система записывает в конфиг B (ключ — я), а не в свой.
6. UI всегда показывает, **какая сторона** режет доступ.

# 2. SCM — уточнения

## 2.1. Где вообще существуют якоря

| Режим | Якоря | Источник заголовка |
|---|---|---|
| **Dynamic** | **нет** | живая сборка на каждый запрос (`MaxVisibleRounds` активен) |
| **Static** | **нет** | снапшот в **конфиге агента**, обновляется только кнопкой |
| **Hybrid SCM** | **да** | снапшот якоря |

В dynamic SCM-объекты не эмитятся и не инжектятся; уже лежащие в истории — инертные данные.

## 2.2. Что такое якорь

**Якорь — это системный промпт**, то есть снапшот **всего заголовка запроса**:

- байты системного промпта;
- **провайдерский tool array** (определения тулов для LLM — это тоже системный промпт);
- всё прочее, что влияет на префикс;
- **плюс изначальное (структурированное) состояние** — база для фолда дельт и вычисления диффов.

Инвариант: **байты и состояние снимаются одним атомарным проходом**, иначе дельта посчитается против
состояния, которого модель никогда не видела.

Следствие: сборка запроса в hybrid — блит замороженных байтов; шаблоны в горячем пути не участвуют,
поэтому правка шаблона не может незаметно изменить замороженный префикс.

## 2.3. Размещение якоря

**Как можно ближе к реальному системному промпту** — то есть на **первое сообщение,
видимое после реза** (на границу региона, который якорь описывает). Не на pending response.

**Правило постановки:** новый якорь ставится **после каждого реза** (чекпоинт любого `Kind`), в том
числе когда заголовок не изменился — суть не в байтах, а в **позиции**: замороженный заголовок должен
быть привязан к региону, который он описывает. Если якорь не найден после новейшего реза — он мёртв,
ставится новый.

**Валидность якоря** = «позиция якоря позже новейшего реза». Позиция — это порядок сообщений (якорь
прикреплён к сообщению) → никаких координат и ID не нужно.

Требования к реализации:

- **`OwnerAgentId` в `AttachedMessageAdditionalViewModel`** (или аналоге). Сегодня `AgentPrivate`
  работает только для assistant-сообщений того же агента, иначе `AttachedMessageInjectionHook` пишет
  `Log.Warning` и игнорирует вложение (`AgentPrivate` срабатывает только при условии
  `assistantMessage.SenderAgentId == agent.Id`).
  Первое видимое после реза сообщение — почти всегда юзерское или чужое-агентское;
- якорь — **одна запись в историческое сообщение на создание эпохи**. Обязателен гейт «якорь уже
  прикреплён и жив → записи нет», иначе per-prep запись в БД (разрушает byte-stability и диагностику);
- якорь — **invisible data**: своего модельного текста у него нет. Об амнезии модель узнаёт из
  чекпоинта, об изменениях — из дельт.

## 2.4. Дельта

```csharp
class ScmDelta : AdditionalChatData
{
    long EpochId;
    long Seq;              // 1, 2, 3…
    long PrevSeq;          // разрывы детектируются без внешнего реестра
    SectionChanges Changes; // машинночитаемая дельта, LOSSLESS и FOLDABLE
    string Content;         // отрендеренный текст, снапшотится при вычислении
    StateAfter State;       // состояние ЭТОЙ эпохи после применения дельты
}
```

- **`Changes` обязан быть lossless и foldable**: `fold(anchor.state, deltas…)` = состояние, с которым
  сравнивается текущее. Lossy может быть **только** `Content`: «Your new persona: <…>» для большой
  персоны можно самаризировать, но сам патч состояния — нет, иначе база для сравнения ломается и
  появляются пропущенные/фантомные дельты.
- **`Content` рендерится один раз, при вычислении дельты, и снапшотится.** Рендер «на инжекте» означал
  бы, что правка шаблона задним числом переписывает уже отправленные дельты — переписывание истории
  назад. Поэтому **рендерер живёт на уровне вычисления дельт**; цена — рост БД, принята.
- Соответственно рендерер — это часть шага «вычисление дельты», а не отдельный сервис: ему нужен
  доступ «назад» (см. 2.5), который даёт announced-состояние.

## 2.5. Состояние эпохи = announced, а не live

**Ключевое решение:** состояние эпохи хранит **не «как есть сейчас», а «что модели уже сказали»**.
Дифф считается между **live-состоянием** и **announced-состоянием**.

Исходы на каждое расхождение:

| Расхождение live vs announced | Исход |
|---|---|
| тул появился / перезаписан / удалён | **announce** + обновить announced |
| тул стал скрыт | **suppress and forget** — дельты нет, announced не трогаем |
| изменилось то, что модель и так видит из свежего базлайна | **suppress and remember** — announced обновляется молча |

Отсюда: сценарий «вкл → выкл → вкл» даёт **ноль дельт** без всякой спецлогики (на «выкл» дельты нет
и announced не меняется, на «вкл» live совпадает с announced).

**Никаких хешей и ID в состоянии — только значения.** Причина: если поменялся источник истины
(переписана персона, изменено описание тула), то по хешу нельзя понять, *что* поменялось, а ссылка на
живую сущность означает живое значение на рендере → байты префикса меняются сами по себе (§ «ничего
не перерендеривается»). Значения дают свежую дельту с содержательной формулировкой.

**Но каноническая форма всё равно нужна.** Сравнение идёт через **каноническую проекцию**
(упорядоченную, нормализованную), и **тот же порядок используется при рендере**. Иначе перестановка
ключей в `args`-схеме тула даст «изменение» → лишняя дельта и лишний разрыв кеша при байт-идентичном
результате.

## 2.6. Секции и «смотреть назад»

Состояние снимается и дельта считается **отдельным провайдером на каждый тип** секции, потому что
только тип знает свою семантику («Tool 'fs-read' become available…», «Your new persona: …»,
«Your persona was reset…»).

Пример дельты для тулов: `string[] OldTools` + `ToolDef[] NewTools` (не только новые, но и
**перезаписанные**), где `ToolDef = { name, desc?, args? }` и `desc/args = null` для скрытых тулов.

**Требование «смотреть назад»** (например: не показывать повторно описания тулов, которые уже лежат
в контексте — сценарий «вкл → выкл → вкл»; и не сообщать, что тул «теперь скрыт»). Обеспечивается
**announced-состоянием по значениям**, а не сканированием истории дельт: сравниваем «что было
анонсировано» с «что предлагается анонсировать». При suppression «скрыт» announced не меняется →
рендер видит «анонсировать нечего».

**Ребейзлайн сбрасывает announced** к тому, что сообщает свежий базлайн. Поэтому:

> **Имена скрытых аддонов обязаны переанонсироваться в initial-дельте новой эпохи** (только имена,
> без `desc`/`args`). Иначе после каждого реза модель молча забывает, что эти тулы вообще существуют
> и вызываемы — из промпта она их не увидит по определению.

## 2.7. Скрытые аддоны в hybrid

**Анонсируем по имени** («Tool 'fs-read' become available, use `addon-info` for its description and
arguments»), детали — по требованию через `addon-info`.

Это не «отступление от silent», а следствие: в **dynamic** канала дельт не существует вообще, поэтому
обсервация там возможна только через `addon-list_available` — молчание там вынужденное. В hybrid
канал есть, и молчание означало бы **принудительный** вызов листинга: платить токенами промпта за
список и ещё раз токенами за то, чтобы модель его запросила. То есть hybrid даёт лучшее знание списка
аддонов при меньшем промпте.

Обязательно фиксируется: **`hidden ≠ unavailable`** (скрытый = «не в листинге, но вызываем»), иначе
«не говорить, что тул теперь скрыт» превратится в ложь для модели, которая этот тул видела.

## 2.8. Чекпоинты как Kind-ы

```csharp
enum CheckPointKind { Summary, Shield, ToolCompaction }

// ЕДИНСТВЕННОЕ место, где Kind превращается в поведение:
public bool IsCut => Kind is Summary or Shield;
```

`ToolCompaction` — полноправный Kind, потому что **ломает кеш ⇒ требует нового якоря**. Он не режет
основной контекст: результаты тулов просто обрезаются. То есть «режет историю» — это **свойство**, а
не определение чекпоинта. Walk обязан спрашивать `IsCut`, а не свитчиться по `Kind` — иначе
добавление четвёртого Kind-а потребует правок у всех потребителей.

**`ToolCompaction`:**

- на рендере результат тула заменяется на `[TOOL RESULT WAS COMPACTED, THE TOOL EXECUTED WAS
  SUCCESSFUL/FAULTED BEFORE]`;
- `ResultContent` **не мутируется** — это подавление на сборке (тот же принцип, что у видимости);
- триггеры: **порог токенов** (как у авто-суммаризации) и **ручная кнопка под сообщением**
  (`MessageExtension`). Общий бюджет триггера с суммаризацией обязателен, иначе два независимых
  авто-порога будут перебазировать кеш вдвое чаще, чем нужно;
- ручной триггер обязан иметь **скоуп** («компактифицировать до этого сообщения») — этот скоуп и есть
  позиция чекпоинта, а от неё зависит, куда встанет якорь;
- **компакция «по мере старения» запрещена**: разрыв кеша каждый раунд убивает hybrid;
- `IsCompactible` — флаг **на тул-коллах** (не на тулах), берётся из `ToolInfo`, записывается в
  `ToolExecutionService` **в момент исполнения** (а не читается из `ToolInfo` на рендере): иначе
  правка флага задним числом меняет рендер уже отправленных сообщений.

## 2.9. Якорь и мультиагентность

**Якорю безразлична мультиагентность.** Видимость агентов (внезапное появление/исчезновение
сообщений) — **другая тема**: у такого изменения нет позиции в истории, значит нет и места, куда
прикрепить якорь. Оно ломает кеш **региона сообщений**, заголовок при этом не меняется.

Из этого — три разных множества событий, которые нельзя путать:

| Множество | Примеры | Следствие |
|---|---|---|
| **Заголовок изменился** | добавлен/убран тул, правка персоны, компоненты, timezone | новый якорь (после ближайшего реза) |
| **Регион сообщений изменился** | правка политики видимости, переименование, режим идентичности | только цена кеша, якорь не трогаем |
| **Разрыв цепочки** | удаление/ветвление сообщения с дельтой, потеря якоря | ребейзлайн с соответствующим reason |

## 2.10. Carve-outs и UI-инварианты

1. **SCM-объекты и `AgentPrivate`-вложения иммунны к фильтру видимости** — иначе (при выключенных
   своих сообщениях) собственные якоря и дельты выпадут из effective set → «нет живого якоря» →
   rebaseline на каждом prep → кеш мёртв, объекты спамятся. Сегодня это латентно, рефакторинг
   видимости сделает живым.
2. **Настройки, несовместимые с hybrid, дизейблятся в UI, а не «молча неактивны»**
   (`MaxVisibleRounds`; выключение своих сообщений / `SelfVisibility.Messages`).
3. Порядок резолва тулов (live → frozen → alias → announced → unknown) берёт frozen-часть **из
   tool array якоря**, а не из отдельного кеша — иначе два источника замороженного.

# 3. Отклонённые варианты (не предлагать повторно)

| Вариант | Почему отклонён |
|---|---|
| Режим скрещивания **И/ИЛИ**, настраиваемый | глобальная скрытая переменная; смысл каждой записи начинает зависеть от режима, ответ на «почему видно» становится невозможен |
| **Зеркальные настройки чтения** (default + оверрайды на стороне читателя) | два источника истины на пару → противоречивые состояния и тихие no-op; заменено на биндинг «на себя» в конфиге отправителя |
| Структура ключа `AuthorRef { Kind, Id }` | избыточна: `string` + `Guid.TryParse` даёт то же самое |
| Автор `System` с фасетами для памяти/скиллов/хуков | системный контент и так гейтится собственными настройками агента; новые сущности не нужны |
| **Авто-удаление** записей, указывающих на отсутствующих авторов | удаление = возврат к дефолту = fail-open |
| `MessagesWithToolCalls` как «пусто после маски ⇒ выпадает» | не решает исходную задачу: сообщение не пустое (есть нарративная преамбула), а ценность флага сценозависима |
| `ChainId` на сообщениях для «текущей цепочки» | избыточно: правило позиционное (непрерывный хвост своих сообщений) |
| Хеши/ID в состоянии секций | по хешу нельзя сказать, *что* изменилось; ссылка на живую сущность меняет байты префикса сама по себе |
| Якорь на **pending response** (tail) | базлайн должен стоять на границе описываемого региона, «как можно ближе к реальному системному промпту» |
| Отдельный тип (не Kind) для `ToolCompaction` | ломает кеш ⇒ по аксиоме требует якоря; Kind-ом он получает постановку якоря бесплатно |
| «Тихий» режим для скрытых аддонов в hybrid | вынуждает модель дёргать `addon-list_available`, который не хочет дёргать лишний раз |
| Расширение, «которое просто починит» видимость на стороне якоря | якорь — заголовок, у видимости нет позиции; это разные темы |
